# Salt All The Things 0.0.1

## Highlights

- Establishes the Foundation release governance baseline and a single cumulative
  release record for issues #4 through #15.
- Invalidates the database credential that had been exposed in tracked
  documentation without logging either the old or replacement value.
- Makes browser and backend configuration environment-aware so one immutable
  source revision can run in local, development, test, and production.
- Adds one reproducible container runtime and pull-request validation path for
  the complete application, migrations, database suite, and browser assets.
- Aligns AI credential-status checks and idea persistence so browser success
  messages reflect acknowledged server writes without exposing provider keys.
- Makes configured show sections a stable contract for generated and manually
  edited episode outlines.
- Makes joke generation, assignment, reassignment, retirement, and idea deletion
  follow one validated and transactional bank contract.
- Prevents stale browser tabs from silently overwriting newer saved data and
  makes save, success, conflict, retry, and failure state visible on every
  authenticated page.
- Establishes an isolated branch-deployment sandbox on the shared development
  server with immutable commit metadata and fail-closed external-service access.
- Adds an isolated test integration gate for the exact approved commit on
  `main`, with fail-closed migrations, metadata, and authenticated smoke checks.
- Makes semantic releases reproducible from one authoritative version and one
  validated curated note, with GitHub Release publication isolated from
  production deployment.
- Replaces direct production delivery with an immutable, validated release-tag
  cutover that preserves the externally managed database and keeps frontend and
  backend artifacts on the same commit.
## Fixes/Changes

- Defines `VERSION` as the authoritative application version and reports `0.0.1`
  through FastAPI metadata and `/api/health`.
- Removes the invalid credential from current tracked documentation.
- Documents the branch, approval, promotion, secret-handling, milestone, and
  parent/child issue contracts for the Foundation release.
- Repairs mocked AI/Drive tests so they reflect server-side OAuth requirements
  and the existing album-art archive behavior.
- Replaces production and legacy-staging browser API origins with same-origin
  `/api` and `/public` routing.
- Adds canonical local, development, test, and production origins plus explicit
  `ENVIRONMENT`/`DATABASE_ENVIRONMENT` ownership checks.
- Rejects production web origins and implicit Google OAuth use in
  non-production; external-service smoke tests require an explicit opt-in and
  still require isolated credentials and Drive resources.
- Extends `/api/health` with environment and commit metadata while returning no
  configuration secrets.
- Adds a safe local startup mode that serves only the public frontend assets
  alongside FastAPI and does not expose `.env`, source, or repository metadata.
- Adds a non-root production image with locked Python dependencies, explicit
  copy boundaries, secret-bearing configuration inspection, and health checks.
- Adds a fail-fast entrypoint that validates environment/data ownership, runs
  Alembic migrations, and then starts FastAPI.
- Adds separate local, development, test, CI, and production Compose
  definitions. Non-production database storage is isolated by project/volume;
  the production definition contains no database service.
- Adds read-only pull-request validation using immutable official action
  revisions. CI constructs only a constrained loopback database connection,
  runs migrations and all database tests, builds the production image, and
  verifies fresh-database health metadata.
- Fixes fresh-database migration bootstrap so the Alembic version table's
  namespace exists before revision `0001` creates application tables.
- Removes browser-side AI key defaults and uses only the server-provided
  `claudeApiKeyConfigured` and `openaiApiKeyConfigured` status fields for idea
  and joke preflight.
- Makes browser data writes await the API response, restores the prior cache
  value on failure, and shows a user-visible error instead of presenting an
  unacknowledged idea, configuration, import, clear, or joke write as saved.
- Persists canonical idea AI provider/model provenance, accepts the legacy
  `aiModel` field during migration, and returns only the canonical fields.
- Makes the server authoritative for idea modification timestamps and uses
  `updatedAt` for idea ordering instead of the discarded `lastModified` field.
- Preserves configured and per-episode section IDs when names are edited.
- Requires non-empty configured sections with unique stable IDs. New AI
  outlines must contain every configured section exactly once with 2-5
  non-empty talking points.
- Normalizes complete reordered model output to configured order and canonical
  names. Missing, duplicate, unknown, or malformed output receives one bounded
  repair attempt and is rejected if still invalid.
- Constrains the episode editor to the historical outline's section identity,
  count, and order while allowing section names and talking points to change.
  Global section configuration changes apply only to future generation and
  never silently rewrite existing episode outlines.
- Compares generated jokes against every unused, used, and retired bank entry
  using case-, whitespace-, Unicode-, and punctuation-normalized exact matching.
  Generated batches must contain the configured number of non-empty strings,
  with no normalized duplicates and no joke longer than 500 characters.
- Rejects invalid joke counts outside 1-20 and malformed AI joke batches with an
  explicit upstream-response error instead of silently dropping invalid values.
- Adds atomic authenticated API operations for assigning, reassigning, freeing,
  and deleting an idea with its joke lifecycle. Browser state is refreshed only
  from the acknowledged canonical response, so reloads preserve the result.
- Serializes joke lifecycle writes and adds database constraints requiring one
  assigned joke per idea, a valid lifecycle status, and agreement between
  `status` and `used_by_idea_id`.
- Normalizes the legacy `active` joke status to `unused`. Retiring a joke frees
  it, moving a joke frees its prior idea, replacing an idea's joke frees the
  previous joke, and deleting an idea preserves its joke as unused.
- Adds a single server-owned data revision to browser-visible application state.
  Every authenticated browser mutation supplies its exact `If-Match` revision;
  missing preconditions are rejected and stale snapshots receive a conflict
  without applying their payload.
- Serializes browser writes across all entity types, cancels queued writes after
  a failure or conflict, reloads canonical state after conflicts, and warns when
  navigation would abandon pending work. Network failures retain a visible
  retry action.
- Replaces multi-request schedule moves and bulk import/clear with transactional
  server operations. Schedule replacement, movement, unassignment, dependent
  deletion, and idea status changes now commit together or roll back together.
- Keeps the legacy full-replace APIs for ideas, jokes, show slots, and
  assignments, but protects them with the global revision and returns one
  canonical browser-safe state after every acknowledged mutation.
- Adds an explicit-branch development deployment workflow that resolves one
  immutable commit, uses strict SSH host trust, creates bounded pre-deploy
  backups, and verifies local and public environment/version/commit metadata.
- Reserves loopback port `8300`, Compose project `satt-development`, and volume
  `satt-development-postgres`; forces Google OAuth values empty and external-
  service opt-in false in the development Compose definition.
- Makes the registered `deploy.yml` entry point manual development-only and
  removes its ordinary push-to-`main` production job. Production deployment is
  isolated in validated tag-only `deploy-prod.yml`.
- Adds a `main`-push-only test workflow that verifies `github.sha`, uses strict
  test-host trust, checks out the exact detached commit, creates bounded SATT-only
  backups, and never targets development or production resources.
- Fixes the test Compose identity to `satt:test` and forces Google OAuth values
  empty with external-service opt-in false.
- Adds a non-production-only deployment smoke helper that refuses production,
  cross-tier databases, non-loopback targets, and external-service opt-in. It
  tests public routes, rejection, registration, repeated login/export, and
  removes its random identity.
- Requires the PostgreSQL health check to observe the final PID-1 server before
  starting the application. Alembic's async environment now opens a committing
  transaction, CI requires `alembic current --check-heads`, and container CI
  directly requires the final database to report revision `0006`.
- Adds strict release validation for canonical semantic versions, required note
  sections, tag/version/filename/heading agreement, instructional template text,
  and credential-shaped content. Pull-request validation runs it with read-only
  permissions and cannot publish.
- Makes development, test, container, and authenticated smoke checks read the
  expected application version from `VERSION` instead of embedding `0.0.1`.
- Adds a `prod-v*` GitHub Release workflow that verifies the immutable tag
  commit belongs to `main`, validates the curated note, and creates or updates
  the matching release without deployment credentials or application commands.
- Adds a standalone production Compose identity, verified custom-format database
  backup tooling, and secret-safe authentication/data continuity fingerprints.
- Adds exact-tag and `main`-ancestry validation, strict production SSH trust,
  safe migration-head checks, bounded local/public health checks, and recovery
  to either the legacy SATT systemd unit or the exact prior SATT image.
- Documents secret-safe production inventory, configuration-name-only preflight,
  the isolated cutover sequence, a 24-hour legacy-runtime rollback window, and
  the separately approved destructive database-restore boundary.

## Rollback

- The rotation job was transactional at the operational level: any failed
  authentication, restart, or health check restored the prior role credential
  and SATT environment file before restarting the service.
- The completed rotation must not be rolled back to the invalidated credential.
- Issue #5 can be rolled back by reverting its focused commit before promotion.
  A rollback must preserve environment-specific server configuration and must
  not restore production or legacy-staging API URLs in non-production browser
  assets.
- Issue #6 can be rolled back before promotion by stopping its Compose project
  and reverting the focused container/CI commits. Named non-production database
  volumes are not removed unless an operator deliberately requests the
  destructive `down --volumes` recovery path.
- Issue #7 can be rolled back by reverting its application commit and
  downgrading revision `0004` to `0003`. The downgrade removes only the two new
  provenance columns, so any provenance recorded after upgrade is lost while
  the pre-existing idea content remains.
- Issue #8 can be rolled back by reverting its focused commit. It adds no
  database revision and never rewrites historical outline data.
- Issue #9 can be rolled back before promotion by reverting its application
  commit and downgrading revision `0005` to `0004`. The downgrade preserves joke
  rows and current assignments but removes the database lifecycle and uniqueness
  backstops and restores the legacy `active` default.
- Issue #10 can be rolled back before promotion by reverting its application
  commit and downgrading revision `0006` to `0005`. The downgrade preserves
  ideas, slots, and assignments but removes the revision row and the one-slot-
  per-idea database backstop; clients must reload after either direction of the
  transition.
- Issue #11 code rollback redeploys a previously validated commit to the same
  isolated Compose project. Repeat deployments take a mode-`0600` SATT-only
  database backup first; restoring or removing its named volume requires a
  separate explicit destructive-action confirmation.
- Issue #12 code rollback redeploys a previously validated `main` commit to the
  same `satt-test` project. An incompatible migration requires stopping only that
  project and restoring its verified pre-deploy backup; deleting
  `satt-test-postgres` requires separate destructive approval.
- Issue #13 can be rolled back before promotion by reverting its focused commit.
  After release, an immutable production tag must never be moved or reused; a
  code correction requires a new patch version, while a compatible operational
  rollback redeploys a previously validated tag.
- Issue #14 rollback automatically restores only the prior SATT application
  runtime when a cutover-stage migration, fingerprint, or health check fails.
  The first cutover keeps the current systemd runtime and proxy path intact for
  24 hours; later releases retain the exact prior image.
- Database restoration is intentionally never automatic. It requires preserving
  the failed state and obtaining separate destructive-action approval against
  the verified release backup and exact migration state.
## Known Limitations

- Test infrastructure, DNS, TLS, and deployment controls are provisioned, but the
  application and database intentionally remain stopped and uncreated until a
  separately approved merge places `deploy-test.yml` on `main`. The public test
  origin returns `502` until that first authorized deployment.
- Live production inventory is incomplete because the available local SSH
  identities are not authorized on that host. The protected GitHub `production`
  environment and its required secret names are also not configured. Both remain
  explicit preflight gates; no server or GitHub configuration was guessed or
  changed.
- GitHub Release publication and tag-gated production deployment are
  implemented but have not been triggered because no production tag is
  authorized. Issue #15 and the release-integration phase still own combined
  development/test validation, the non-production recovery exercise, and the
  separate production decision.
- No production tag or deployment is authorized; version `0.0.1` is not shipped.
- Docker, Bash, and PostgreSQL are unavailable in the local Windows workspace,
  so committed migration, clean-image, and fresh-container evidence comes from
  the successful isolated pull-request jobs.
- Development intentionally has no OAuth, AI provider, or Drive credentials and
  no external-service opt-in. Provider/Drive smoke is therefore intentionally
  excluded rather than using production credentials or resources.
- The fresh development database has no retained smoke account. Manual
  authenticated testing requires a separate development-only account created
  through the invite flow; production credentials must never be reused.
- Empty show-section configuration intentionally blocks new AI outline
  generation; custom configurations must be non-empty with unique stable IDs.
- Joke duplicate rejection is normalized-exact, not semantic similarity, and
  revision `0005` does not automatically delete pre-existing duplicates.
- The data revision is intentionally global. A stale tab is rejected and must
  reload/reapply its intended change; the application does not auto-merge
  full-array payloads.
